SLIDE 3
Technical Architecture: SPA + Spring Boot

Purpose:
Map out the architectural stack.

Description:
A comprehensive mapping of the core technologies powering the front-end SPA and the back-end Spring Boot service layers.

Features:
* Client Tier: Vanilla HTML5, CSS3, ES6 JavaScript, GSAP, and ScrollTrigger
* Routing: Lightweight client-side browser history intercept router
* Server Tier: Java 21, Spring Boot 3.5, Spring Security, Hibernate ORM
* Database: H2 in-memory database with automatic DDL schemas

User Actions:
* Client interaction triggers async fetches to REST endpoints without page refresh

System Actions:
* Spring Boot boots, runs Hibernate schema updates, populates H2 using CommandLineRunner database seeder
* JavaScript routes request JSON data from REST APIs and dynamically renders DOM templates

UI Components:
* Main Container: <main id="app"> which receives swapped fragments
* Loader: CSS spinner (.page-transitioning) during dynamic route fetches

Business Rules:
* All non-API requests are forwarded to index.html to allow client-side deep linking.

Image Suggestion:
A technical block-diagram layout showing the relationship between Client (HTML/JS/GSAP), REST API Controllers, Spring Services, Spring Data Repositories, and the H2 Database.

Speaker Notes:
"PLUS33 runs on a modular monolith stack. We use Spring Boot to expose clean REST endpoints, and vanilla JS to swap views inside a single page container, avoiding the overhead of heavy frameworks like React."

SLIDE 5
SPA Client-Side Routing System

Purpose:
Explain the SPA routing mechanics.

Description:
Technical walkthrough of the client-side router (router.js) that intercepts browser requests, matches paths, handles history state, and drives page controllers.

Features:
* Path Matching: Regex-like matching mapping paths like '/product/:id' to dynamic parameters
* History Management: Uses HTML5 History API (pushState/popstate) to navigate without full reloads
* Asset Isolation: Dynamically injects page-specific CSS files on demand
* Lifecycle Hooks: Invokes init() and destroy() functions to initialize and clean up JS memory

User Actions:
* Click navigation link: Intercepted by router
* Click browser back/forward buttons: Triggers popstate transition

System Actions:
* Fetches HTML fragment from server, swaps it into '#app', swaps page titles, updates CSS links, and executes controller callbacks

UI Components:
* Page Transition Overlay: Glassmorphic fade wrapper
* Navigation Active Tags: CSS class `.active` dynamically mapped to links

Business Rules:
* Invalid paths fallback to a dedicated editorial 404 block with back-navigation.

Image Suggestion:
A flowchart showing: Intercept Click -> Transition Out -> Fetch HTML Fragment -> Swap DOM -> Load CSS -> Trigger Init Page Script -> Transition In.

Speaker Notes:
"The client-side router handles navigation seamlessly. It intercepts all internal clicks, fetches html segments asynchronously, swaps the page body, loads target CSS files, and calls custom init and destroy handlers to prevent memory leaks."
